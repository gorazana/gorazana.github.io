History

Reusable command history and undo/redo primitives for editors, with explicit limits on reversing durable or external effects.

Responsibilities and capabilities

This is a research contract. An implementation, tag or icon alone does not establish that every listed capability is shipped or verified.

  • HISTORY-01Typed command/effect contract with execute, inverse and revision preconditions
  • HISTORY-02Independent bounded histories per document/workspace
  • HISTORY-03Undo, redo, clean/save markers, grouped commands and safe coalescing
  • HISTORY-04Branch truncation after a new edit and explicit history limits
  • HISTORY-05Optional durable journal/snapshot adapters with codec versions and integrity
  • HISTORY-06Renderer-independent state for keyboard/menu/history views

Where this component stops

A reusable technical core with native Goravel adapters; no application-specific schema or required paid platform. Undo is not deletion of the security audit trail

Model and lifecycle

HistoryID, CommandEnvelope, ExpectedRevision, InversePayload, Group, CleanMarker, Snapshot, JournalReceipt

Validate command then apply to authorized target then record successful effect then advance history; undo/redo revalidates target revision and current authority.

Dependencies, deliberately chosen

Native Goravel capabilities

  • Config
  • Log
  • ServiceProvider/factory
  • Events
  • optional persistence adapter

Go and candidate adapters

  • context
  • sync
  • encoding/json; bounded command/journal codec

Optional Gorazana integration ports

ActivityAuditDocuments

These are replaceable capability ports, not a blanket requirement to install every named package. Mandatory dependency claims require a tested implementation profile.

Operational requirements

Host-selected authoritative persistence and necessary native workers. External services are opt-in, with explicit credentials, costs and capability/evidence profiles.

Safety and acceptance

  • Undo is not deletion of the security audit trail
  • A refund or sent email is not reversed by popping a stack
  • Shared editing requires a separate conflict/operation model, not a global stack
  • Failed commands never advance the cursor
  • Persisted payloads are bounded data and never arbitrary serialized Go closures
  • Negative and boundary tests for each stated invariant
  • Concurrent/stale revision and duplicate-command tests for the principal transition
  • Real selected database transaction, migration-upgrade and recovery tests
  • Cross-scope list/detail/count/export/relationship checks
  • No real external side effects in ordinary fixtures; live-provider tests separately labeled
  • Selected renderer tested for validation, keyboard, narrow layout and error states

The referenced primary projects/standards inform terminology or comparable boundaries. Feature/state/security requirements here are authored Gorazana proposals, not claims that those projects implement the same contract. None of these specimens is completed software.
