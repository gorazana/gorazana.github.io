Model & lifecycle

Typed contracts, owned persistence and configuration are preserved in SOURCE_REFERENCE.md, original sections 5–6. Adapt to the actual implementation; these are not applied migrations.

Source transaction records event/outbox → select authorized active subscriptions → persist one delivery per endpoint → acquire fenced lease → resolve and validate destination at connection → sign exact stored bytes → send with stable ID/timestamp → record accepted/retryable/permanent/uncertain outcome. Inbound route limits body and preserves bytes before decoding; verifier validates provider signature and timestamp; receipt and domain processing intent commit before 2xx. Processing can then be asynchronous and idempotent. Do not acknowledge a failed durable receipt merely to avoid retries. ### Network and retry defaults Do not disable TLS verification to make development callbacks work. A dedicated local test transport can be injected in tests and must not be selectable by untrusted requests. Provider POST success is acknowledgement, not proof the subscriber applied the business change. Replay uses the original identity and a new delivery attempt, never silently a new event ID. Receiver deduplication is documented as part of the integration contract.

Operational requirements

A bounded outbound worker and provider-specific inbound verification; disabled until endpoints/policies configured. Optional expanded profile: Per-tenant subscriptions, operator-approved egress, rotation, dead-letter workflows, high-volume delivery and separate provider adapters.
