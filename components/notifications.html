Where this component stops

No marketing-consent compliance promise, no guarantee exactly-once external delivery, no generic outbound webhooks substitute, and no mandatory SMS/cloud subscription.

Model & lifecycle

Typed contracts, owned persistence and configuration are preserved in SOURCE_REFERENCE.md, original sections 5–6. Adapt to the actual implementation; these are not applied migrations.

Authorize sending category → resolve recipient and current preferences → validate template payload → persist intent/outbox → worker acquires fenced lease → recheck cancellation/consent → render trusted versioned template in locale → invoke channel with stable idempotency key → persist accepted/failed/uncertain. A provider accepting a message is not proof of delivery. A timeout after send is uncertain; reconciliation or provider idempotency is required before retry. In-app read status is a separate authorized mutation. ### Exactly-once wording The durable intent is unique inside its store. The external channel may still produce duplicates when a network failure hides a successful send. Do not convert that uncertainty into a false failed status or a guarantee of exactly-once delivery. Sensitive one-time challenges belong to Defender delivery contracts; forwarding them must never persist plaintext in a generic notification timeline.

Operational requirements

In-app and native email; synchronous mode explicit for small bounded transactional messages. Optional expanded profile: Durable dispatch, preference service, provider failover only with duplicate-risk handling, quiet hours, escalation integration and delivery diagnostics.
