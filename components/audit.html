Where this component stops

No claim of statutory certification, absolute immutability against an administrator controlling store+keys+anchors, legal advice, raw secret archive or replacement for source transactional audit records.

Model & lifecycle

Typed contracts, owned persistence and configuration are preserved in SOURCE_REFERENCE.md, original sections 5–6. Adapt to the actual implementation; these are not applied migrations.

Authenticate issuer/scope → validate canonical envelope and redaction → same-store sequence/hash append → return receipt → background signer creates deterministic checkpoint → independently anchor/store under configured retention. Verify recomputes each entry and chain and checks signed/anchored head; a local chain alone cannot prove a truncated tail never existed. Export carries exact canonical bytes and public key references. Retention deletion needs current hold checks and storage capability acknowledgement; failed deletion remains pending, not falsely purged. ### Threat model must appear in README A malicious database administrator with access only to the SQL store may alter a local chain; an independent signed checkpoint can expose that. An administrator who also controls signer keys and anchor storage may forge a replacement history. State which role controls each component and the evidence latency. WORM object storage, external time-stamping and legal requirements are separate capabilities with their own verification, not automatic consequences of using SHA-256.

Operational requirements

SQL append store plus verifiable export; explicitly label as tamper-evident only against the defined attacker. Optional expanded profile: Independent signer/anchor, object-lock retention and separable roles for ingest, retention administration and verification.
